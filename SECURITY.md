# Security model

Cove assumes untrusted browsers, arbitrary user-controlled messages/files, forged API requests, malicious invite holders, and curious community members. The React UI is *not* an authorization boundary. PostgreSQL and API-side decisions determine who may read/write every community, private channel, conversation and attachment. This is an engineering baseline, **not a completed third-party security audit**.

## Implemented controls

- **Identity:** Argon2id password hashes; random 256-bit opaque session/invitation/verification tokens with only hashes at rest; sessions have expiry, revocation and device listings. No access tokens in `localStorage`. Cookies are HttpOnly (session), Secure in production, SameSite=Lax. Authentication rechecks DB sessions; password reset revokes all sessions and sockets. OAuth uses Google code+PKCE with a signed, expiring state cookie and verified ID token; it does not silently link an existing password account.
- **Cross-site requests:** authenticated state-changing REST requires a CSRF header matching the separate readable CSRF cookie and session hash. HTTP `Origin`/CORS allowlists apply, including to credentialed requests. Engine.IO's `allowRequest` additionally rejects unapproved **WebSocket upgrade** origins (CORS by itself does not protect WebSocket). Browser Socket.IO connections require the HTTP-only cookie and validate the session on every packet.
- **Access:** permission and hierarchy evaluation is performed on the API for REST and Socket.IO. Private channels must have an explicit view grant; inaccessible channels return 404 and are excluded from lists, search, history and attachments. DMs/groups require conversation membership and are forbidden in either direction after a block. Invite acceptance checks bans and atomically consumes usage. Role assignment cannot outrank the actor; only the owner can transfer or delete a community.
- **Abuse limits:** Zod validates JSON and UUIDs; API limits JSON to 64 KiB; Socket.IO limits packet size to 64 KiB and 100 client events/10 seconds. General HTTP rate limit is 180 requests/minute, auth attempts 15/15 minutes (test environment higher), messages 15 new sends/10 seconds. Redis backs these limits for a multi-instance deployment; without Redis, *only one* API instance is supported. File size/type, per-user quota, maximum attachments and detected MIME/extension are checked. Uploads require authenticated CSRF and private reads require access checks.
- **Delivery/consistency:** messages commit to PostgreSQL before an HTTP response/Socket.IO acknowledgement or broadcast. Unique nonces and matching-payload checks prevent accidental duplicates. Edits/deletes/reactions/pins recheck rights. `lastReadAt`, notifications, reports, bans and audit entries are persisted. WebSocket user/channel rooms are not substitutes for the DB checks.
- **Browser/server:** user message text is React-escaped (no raw HTML rendering). API error responses are sanitized and include request IDs, not stack traces. Cookies/CSRF headers are redacted from HTTP logs. Download responses set MIME, `nosniff`, private/no-store and attachment disposition for non-images. Production web pages include CSP, HSTS, Referrer-Policy, Permissions-Policy and no `X-Powered-By` header. TLS is required in front of production web/API.

## Important limitations and operator responsibilities

1. **Third-party verification:** No real Google, SMTP, Cloudinary/S3 or LiveKit credentials were supplied for end-to-end testing. These integrations use their actual SDKs/configuration—not simulated successes—but must be tested on your staging environment. LiveKit webhooks require a valid signature. Enforce provider credentials, quotas and restrictive cloud bucket policies.
2. **Content/file safety:** MIME/signature checks are not malware scanning, content moderation, EXIF stripping, transcoding or a safe-preview service. Do not treat user uploads as trusted. Keep object stores private; configure retention/reconciliation for blobs orphaned by hard deletion of DB records. The built-in cleanup removes only old **unclaimed** uploads; it uses row locks with avatar/icon assignments, but object-store deletion cannot be made atomic with the database.
3. **CSP tradeoff:** Next framework hydration requires `'unsafe-inline'` scripts/styles in this implementation. A nonce/hash-based CSP would reduce script-injection impact further. Restrict external asset origins in deployment and test LiveKit under the final CSP. No browser push notifications or end-to-end encryption is implemented; operators can read database content, and LiveKit is a separate media service.
4. **Distributed/operational controls:** Local file storage and in-memory presence/limits are development/single-instance only. Production requires durable Cloudinary/S3, SMTP, PostgreSQL backup/restore, TLS, centralized logging/alerting and Redis before multi-instance scaling. There is no self-service full account deletion/export, object-store deletion worker for hard-deleted communities, load test, or formal penetration test. Community icon URLs on public invite previews may require login to fetch the underlying protected image; text and name remain visible.
5. **Dependency review:** At verification time, `npm audit` reports **11 advisories (9 high, 2 moderate; 0 critical)**, concentrated in Prisma 6 CLI/its transitive packages and Tailwind 3 build tooling. `npm audit --omit=dev` still reports **4 high** through Prisma CLI's optional peer relationship with `@prisma/client`; that is *not* a clean production audit. Upgrading Prisma to 7 and Tailwind to 4 needs coordinated schema/build migrations; do not claim the supply chain is cleared. Re-run `npm audit`, isolate build tooling from production images, and review/upstream-fix these before a sensitive deployment. Runtime Next, Nodemailer and upload file-type packages were updated to versions not flagged in that audit; this is not a guarantee of security.

## Reporting and deploying safely

Do not include live credentials or private message content in issues/PRs. Rotate `SESSION_SECRET`, SMTP/Google/LiveKit/object-store keys if leaked; revoking all sessions requires a database update or session-table invalidation as well as secret rotation. Set `WEB_ORIGIN` and `GOOGLE_REDIRECT_URI` to the external **HTTPS web origin**, ensure reverse-proxy WebSocket upgrades and forwarded IP configuration, and reject unknown origins. Run migrations as a separate controlled step, monitor `/api/ready`, and test restore procedures. See [DEPLOYMENT.md](DEPLOYMENT.md) and [ENGINEERING_REPORT.md](ENGINEERING_REPORT.md).
